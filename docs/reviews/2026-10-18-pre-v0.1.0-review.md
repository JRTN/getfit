## Verdict

- **Is it going to work?**
  - **Yes, for what exists.** The foundations are sound: stamped transactional writes, tombstones, owner scoping, a day boundary that DST can't break, and a reactive data layer. Two things are at risk:
  - **The backup design leans on an assumption that is probably false.** Google Drive likely can't be chosen as a folder on Android, so the daily snapshot would stay on the phone (§2.1).
  - **Scope.** The milestone order delays the owner's most important daily habit (food logging) to M4, and the "bulk building" pain point that motivated the project has no first-class support in the design (§4.1–4.2).
- **Can it be extended?**
  - **Mostly yes.** Module boundaries, the metric registry, and an explicit-migration database that only grows by added tables and columns are the right shapes.
  - **A handful of contracts need adjusting before M2,** because M2 is when metric IDs, user-defined types and saved charts start becoming stored user data (§3).
  - **Nothing found requires changing the v1 tables themselves.** What must be settled now is what stored values *mean*: enum names, unit codes, entered units, and restorable backup versions (§1).
- **How is the codebase?**
  - **High quality for its age.** It is consistent, thoroughly documented, test-first, and machine-enforced, and CI is green.
  - **The main debts:**
    - business logic living in ViewModels and duplicated between Home and Body;
    - no logging at all;
    - an app shell that owns the only top bar;
    - a deferred-items backlog that lives outside the repo.

## 1. Before locking the schema and tagging 0.1.0

Once real data exists, changing what a stored value *means* costs a data migration. These are the meanings not yet fixed.

**1.1 Enum names are now storage codes. Medium.**
- **Where they're stored:** Room stores enums by constant name: `MeasurementSource`, `MeasurementCategory`, `DailyAggregation` and `Sex`. The planned JSON export stores them the same way.
- **The risk:** renaming a constant (`IMPORT` → `FILE_IMPORT`) makes every existing row unreadable. Room throws on an unknown name and fails the whole query.
- **Fix:** give each stored enum an explicit, permanent code with a converter, or add an architecture test that snapshots the stored names so a rename fails CI. Do this before the pin.

**1.2 `enteredUnit` has no vocabulary. Medium.**
- **Where it comes from:** the "as typed" unit on every measurement is free text produced inside a feature: `BodyViewModel.kt:222` maps `MassUnit` to `"lb"`/`"kg"`.
- **The gap:** M1d's Task 1 fixes the vocabulary of `canonicalUnit` only. `enteredUnit` is user data too, and later milestones add more typed units: in, cm, ft+in, mi, km, %, possibly st.
- **Fix:** define display-unit codes in `:core:model` next to the stored-unit list, and have the import and restore checks validate them.

**1.3 The planned unit list is incomplete, so say explicitly that it grows. Low.**
- **What's missing:** Task 1's `StandardUnit` lacks units M2–M4 need:
  - volume (hydration is canonically milliliters per the design's code conventions);
  - breaths per minute (respiratory rate);
  - body temperature;
  - the nutrient units g, mg, µg and IU, if nutrient metrics use the same descriptor.
- **Why it's only Low:** adding enum values is cheap. The plan should say so: "codes are permanent; the list grows; a code's meaning never changes".

**1.4 The seeder can never correct a built-in row. Medium.**
- **Where:** `ReferenceSeeder` inserts with `OnConflictStrategy.IGNORE` (`ReferenceSeeder.kt:53`), and its KDoc promises "existing rows are never overwritten".
- **The risk:** raising the dataset version only adds new rows. M2 adds a dozen built-in types. When one ships with a wrong `decimals`, display name or Health Connect record type, no release can fix it without a hand-written migration.
- **Fix:** built-ins are owner-less reference data with `localRevision = 0`, so upsert them when the dataset version rises.

**1.5 The release version is still 0.0.1, and nothing in the plan bumps it. Low.**
`VERSION_NAME` is hard-coded in `AndroidApplicationConventionPlugin.kt:83`. The design says it is "bumped by hand in the tagged commit", but M1d's last task doesn't include that step.

**1.6 The release build hasn't been used on a device since M0. Medium.**
- **The gap:** 0.1.0 is "the first usable release", and the release build is different from what has been tested: R8 minification and resource shrinking, a different `applicationId`, separate data. Every drill so far ran on the debug build.
- **Fix:** before tagging, install the release APK, log weights, back up and restore. Kotlinx.serialization navigation keys, Hilt and Vico all depend on keep rules from their libraries.

## 2. In the M1d plan, before running it

**2.1 Google Drive probably can't be chosen as the backup folder. High.**
- **Where the assumption is:**
  - the design: "a folder chosen once via the Storage Access Framework (e.g. a Drive-synced folder)";
  - the plan's Settings copy: "Choose a folder, such as one synced to Google Drive".
- **The evidence:** community reports say Google Drive's Android provider does **not** support `ACTION_OPEN_DOCUMENT_TREE`. It appears for saving single files but not for choosing a folder. ([Cryptomator forum](https://community.cryptomator.org/t/cryptomator-not-usable-without-webdav-or-not-listed-cloud-storages/11933/16); background in [Android's documents guide](https://developer.android.com/training/data-storage/shared/documents-files)). I found no official statement either way.
- **Why it matters:** if it's true, the daily snapshot can only go to local storage, which dies with the phone. Then the layer protects against a corrupted database or a bad update, but not against losing the phone. Android also has no built-in "Drive-synced local folder".
- **Fix:** spend five minutes on the S25 trying the system folder picker, before Task 7 is written. If Drive isn't offered, choose one of these and write it into the design:
  - accept a local folder plus a third-party sync app (FolderSync, Autosync);
  - a provider that supports folders, if one is installed;
  - Drive's REST API, which needs a Google Cloud project and sign-in, which the design avoids;
  - a weekly reminder to "Export data" with `CreateDocument`, which Drive does support.

**2.2 A backup made today must still restore next year. High.**
- **Where:** Task 4's `inspectSnapshot(file, expectedVersion, expectedIdentityHash)` and call 7 require `user_version` and `identity_hash` to *equal* the current ones.
- **The risk:** after the first migration (M2), every 0.1.0 snapshot would be rejected as "not a GetFit backup".
- **Fix:** accept any `user_version` ≤ current, and check its hash against a version-to-hash table kept in `:core:database`, starting `{1: "0cf6…"}`. Room migrates the restored file when it opens. The same rule applies to JSON: v1 decoding must keep working after a v2 format exists. Pin both in tests now, while there's only one version.

**2.3 The merge should match natural keys generally, not only for day-start settings. Medium (bites after M2).**
- **The risk:** call 5 matches `DayBoundarySetting` by date, but `Measurement` has a unique `(ownerId, source, externalId)`. After Health Connect import exists, restoring a JSON file from another install that imported the same records would hit that unique index with different IDs and abort the whole import.
- **Fix:** when `externalId` is set, match on `(source, externalId)`, and state the rule once: "rows with a natural key merge by that key".

**2.4 `AppVersion` from `BuildConfig` won't compile as written. Low.**
`buildConfig` isn't enabled anywhere. Either enable it in the application plugin, or read `PackageManager.getPackageInfo(...).versionName`.

**2.5 The daily snapshot may silently stop on a Samsung phone. Low to Medium.**
One UI's battery management delays or skips periodic work for apps it considers unused. A daily-use app is usually fine, but add a fallback: if the last success is more than 36 hours old, run a snapshot when the app opens.

**2.6 Snapshot names use local time. Low.**
When clocks fall back for DST, `20261101-0130` can occur twice, and pruning by name could delete the newer file. Use UTC in the file name.

**2.7 Exported files are unencrypted health data. Low.**
Say so once in the export dialog or its hint text, and in the developer docs. Auto Backup to Google is encrypted with the screen lock; JSON and `.db` copies in a user folder are not.

**2.8 The restart may race. Low.**
Calling `Runtime.exit(0)` straight after `startActivity` usually works, but can kill the process before the new task launches. A dedicated restart process (the ProcessPhoenix pattern) is more reliable.

## 3. Settle before M2 (these become stored user data in M2)

**3.1 The metric ID scheme is inconsistent, and saved charts will store these IDs. Medium to High.**
- **The inconsistency:**
  - the design says metric IDs are "`body.<measurement type key>` for every `MeasurementType`" (`initial_design.md`, metric inventory), and `MeasurementTypeKeys` repeats this;
  - but the Health Connect table maps to `vital.heart_rate`, `vital.spo2` and `activity.steps`, which are also measurement types.
- **Why now:** M2 stores metric IDs in `SavedChart.specJson`, and later in `MetricTarget.metricId`. A rename after that is a data migration.
- **Fix:** pick one rule. Also decide whether user-defined types are identified by key (which must then never change) or by type ID.

**3.2 User-defined measurement types can hide future built-ins. Medium.**
- **The risk:** `findByKey` prefers the owner's row over a built-in with the same key. If the user creates "body_fat" in M2 and a later release ships a built-in "body_fat", Health Connect imports go to the built-in and manual entries to the custom type. The data splits silently.
- **Fix:** namespace user keys (for example `custom.<slug>`) from the start.

**3.3 The metric contract can't name user-defined metrics. Medium.**
- **Where:** `MetricDescriptor.displayNameResource: Int` (`MetricContract.kt:53`).
- **The problem:** an Android string resource can't name a user's custom measurement type (M2), an exercise's e1RM metric (M3), or a projection plan's series (M5). It is also an Android concept inside a module meant to stay platform-free.
- **Related:** built-in types store an English `displayName` in the database (`ReferenceSeeder.kt:67`), which breaks "every user-visible string is a resource" if it's ever shown.
- **Fix:** use a small `MetricLabel` type, either a resource key or literal text, resolved in `:core:ui`. Built-ins are displayed from resources, never from the database.

**3.4 Source priority has no home in the read path yet. Medium.**
- **The gap:** `BodyMetricProvider` takes "the day's last reading by start time" whatever its source. The design's rule is "manual wins, then `SourcePriority` rank, then the most recent `updatedAt`".
- **What's undefined:** whether that applies per reading or per day. For example, if there's a manual weigh-in today, are Fitbit scale readings ignored entirely?
- **Fix:** define it per day, per type, in the M2 plan, as a domain function the providers share.

**3.5 Health Connect aggregates conflict with the import design. Medium.**
- **The conflict:** heart rate is "aggregated to daily min/mean/max on import", and steps come from the aggregate API. But the import is incremental through change tokens, which deliver individual records.
- **What the M2 plan must decide:**
  - re-aggregating the affected days whenever their records change;
  - synthetic IDs for aggregate rows (for example `hr:2026-10-18`);
  - where three numbers go (min/mean/max), since `Measurement` has one value and one secondary value;
  - documenting this as a deliberate exception to guiding rule 1, "store raw observations".

**3.6 Charts with several series break the redundant-encoding rule. Medium (accessibility).**
- **The problem:** `MetricChart` draws every main series solid with dots, in palette order (`MetricChart.kt:164`), so two series differ only by color. Past six series, colors repeat.
- **What the spec requires:** a distinct dash or marker per series, plus direct end-of-line labels, before the M2 chart builder puts several series on one chart.
- **Also:** the legend is a `Row` that doesn't wrap at 200% font size, and every series gets its own dotted trend line, which clutters quickly.

**3.7 The app shell owns the only top bar. Medium.**
- **Where:** `GetFitApp` draws one `TopAppBar` (`GetFitApp.kt:94`) with the tab's title, and a back arrow only for Settings.
- **What it blocks:**
  - pushed screens can't set their own title or back action: the M2 chart builder and chart editor, the M3 live workout, exercise detail and template editor;
  - multi-select can't swap in its contextual action bar, which the spec requires.
- **Fix:** decide the pattern before M2, either each screen owning its `Scaffold` and top bar, or a top-bar state the shell renders.

**3.8 The ViewModel architecture rule will reject screens that need an argument. Low.**
`ViewModelDependencyRulesTest` allows only `:core:domain` interfaces as constructor parameters. A chart editor needs a chart ID, through `SavedStateHandle` or Hilt assisted injection. Plan an explicit allow-list.

## 4. Upcoming design (M3 to M5)

**4.1 The pain point that started the project has no first-class support. High (product).**
- **What was promised:** the README says the problem is "adding a week of meals, a dozen exercises, or a whole training block", with "multi-select, batch edits and templates … planned as first-class features".
- **What the design covers:**
  - **Food:** multi-select copy and move, recipes, and planned/consumed status. It has no **saved meals or meal templates**, and no way to plan a week from a template.
  - **Training:** routine templates exist, but **programs and blocks are deferred to v2** (`Program → Block → Week`).
- **Fix:** decide now whether "bulk building" means more than multi-select. If it does, add saved meals (M4) and a minimal block (M3) to the design. Your memory note already says to revisit this before the M3 and M4 UI.

**4.2 The milestone order delays daily value. Medium (product call).**
- **The order:** Nutrition, the habit that took you from 330 to 210 lb, is M4. Until M3 and M4 ship, GetFit runs alongside Cronometer and Strong.
- **The mismatch:** the M2 chart builder arrives when the only cross-domain data is weight, sleep and heart rate. The questions in the README (food against training against weight) need M3 and M4 data.
- **An option:** M2 ships Health Connect basics only, the builder moves to after Nutrition, and Nutrition moves earlier. This is your call; I'm flagging the trade-off, not deciding it.

**4.3 The rest timer needs a platform decision. Medium (M3).**
Android 14 and later require every foreground service to declare a type, and none fit a gym timer cleanly:
- `shortService` times out after about 3 minutes;
- `specialUse` needs a justification, which only matters for Play;
- exact alarms are denied by default for new installs.

Decide early between a typed foreground service, or a notification with a countdown chronometer plus an inexact alarm.

**4.4 Process death mid-workout lands on Home. Low to Medium (M3).**
The tab back stack isn't saved across process death (`MainViewModel` says so). The sets are safe in Room, but the user loses their place. The Training tab should offer "Resume workout" for an in-progress session, or the back stack should be saveable (the navigation keys are already `@Serializable`).

**4.5 Sync readiness has two gaps. Medium, not urgent.**
- **(a) Natural-key rows get random IDs:**
  - **Affected tables:** `DayBoundarySetting` (unique by date) and the planned `DayLog`, `MetricTarget`, `ExerciseOverride` and `HomePinnedMeasurement`.
  - **The risk:** two devices can create the same natural key with different UUIDs. Last-writer-wins *by id* never reconciles them, and the unique index rejects one.
  - **Fix:** derive UUIDv5 IDs from the natural key, for example `daylog:<owner>:<date>`. This needs no schema change.
- **(b) Child tables don't fit the sync contract:** `FoodNutrient`, `ServingSize`, `RecipeIngredient`, `ExerciseMuscle` and `SleepStage` have composite keys and no `id`, owner or revision columns. `SyncableChange` assumes `rowId: Uuid`. Decide before M4 whether children travel inside their parent's payload ("aggregate sync"). Food versions are immutable aggregates, which suits that.
- **(c) Last-writer-wins on device wall-clock time** can let a stale write win when clocks drift. A hybrid logical clock column can come with sync. Low.

**4.6 The query pattern won't scale to nutrition. Medium (M2 and M4).**
- **The pattern:** Body and Home subscribe to *all history* and recompute in Kotlin. Room re-runs a query on every write to its table, and the `Measurement` table will hold every Health Connect type. So each import burst re-reads and re-maps all weigh-ins, twice in Body's case (`BodyViewModel.kt:168-169`).
- **What M4 needs:** diary totals across years must be SQL aggregates over bounded ranges.
- **Fix:** set the convention in the M2 plan.

**4.7 Smaller design notes:**
- **Long-range charts (Low to Medium):** "All" over years draws thousands of dots. Bucket by week or month automatically (bucketing already exists in the domain layer).
- **Projection solver (Low):** "Physically impossible" means a required intake below 0, but bisection over `[0, 2 × E₀]` can't return a negative. First check whether fasting (I = 0) misses the target.
- **Importers (Low):**
  - Strong's CSV has no unit column, so ask for the unit.
  - Cronometer's export is per entry, not per food, so the M4 plan must decide how entries become food versions without duplicates.
- **Reference database (Low):** `reference.db`'s "replaced wholesale" conflicts with `createFromAsset`, which copies only once, and with the destructive-migration rule. This is already in your deferred list.
- **Multiple users (Low):** DataStore preferences are per install, not per owner. That's fine until multiple users arrive.

## 5. Codebase health (developer view)

**Strong:**
- **Data integrity:**
  - `StampedWriter` is the one write path;
  - tombstones are filtered in every DAO;
  - owner isolation is tested with two owners at both the DAO and repository levels;
  - `localDateFor` can't be broken by DST;
  - preferences survive corrupt files and unknown values.
- **Rules enforced by machines:**
  - detekt rules for color literals, dispatchers and destructive migrations;
  - Konsist rules for pure modules, feature isolation, ViewModel dependencies and DAO owner scoping;
  - a contrast test for every palette;
  - dependency analysis.
- **Tests:** they test behavior rather than mocks, and use hand-written fakes and live Room. A mutation check was used where reactivity mattered.
- **Clean code:** consistent explicit style, KDoc that explains *why*, no TODOs.
- **Docs:** the developer guide is among the best I've seen for a project this size.

**Debts:**
- **5.1 Business logic lives in ViewModels, duplicated between Home and Body. Medium.**
  - **What's duplicated:**
    - the history start (three copies);
    - unit conversion (two copies);
    - the range-to-dates-to-rate pipeline, computed independently in `HomeViewModel` and `BodyViewModel`.
  - **Why it matters:** the "−1.4 vs −3.7 lb/week" confusion came from exactly this. As Nutrition and Training arrive, every card and tab would re-implement summaries.
  - **Fix:** the nav spec's `SummaryRule` is the right fix. Make it a domain function the ViewModels call, and move weight's rate onto it first.
- **5.2 There is no logging at all. Medium.**
  - **The gap:** the spec calls for a logging interface in `:core:model`, and nothing logs anywhere.
  - **Why now:** M1d adds background work and M2 adds a background importer. Without logs, a failed overnight import is invisible.
  - **Fix:** add the interface and a file-backed logger (rotated, next to the crash logs) with the first worker.
- **5.3 One bad time zone breaks a whole list. Low to Medium.**
  `Converters.timeZoneFromId` calls `TimeZone.of`, which throws on an unknown ID (`Converters.kt:52`). One row from a device with newer time-zone data makes the whole query fail. Fall back to a fixed offset or UTC and keep the raw ID.
- **5.4 Small items. Low.**
  - Unit symbols are defined in a feature.
  - "value unit" is built by string concatenation (`HomeScreen.kt`) rather than through a resource.
  - Stale comment: "Five labels" in `GetFitApp.kt:138`.
  - `TopLevelBackStack.backStack` is unused (already deferred).
- **5.5 detekt 2.0.0-alpha.6 is a hard CI gate. Low.**
  It's an alpha. Expect occasional breakage on upgrades, and pin it deliberately.
- **5.6 No tests run on a device. Low to Medium.**
  Everything runs in Robolectric, and the TalkBack listening pass hasn't happened. The spec planned on-device UI semantic tests "before releases". Run the release-build smoke test (§1.6) and the TalkBack pass together before 0.1.0.

## 6. The app today (user view)

- **6.1 Body's headline rate becomes meaningless as history grows. Medium.**
  - **The problem:** Body defaults to **All**, and the rate is the least-squares slope across the whole range. After a year with a gain then a loss, "−0.2 lb/week since Oct 2025" says nothing about this month.
  - **Options:**
    - default Body to 30 days;
    - always show a recent rate next to the range's rate;
    - cap the rate window.

  This is your call, since you chose All.
- **6.2 Correcting entries (Low, already deferred):** there's no way to edit a weigh-in (a typo means delete and re-add), no undo for delete, and no message when a save fails.
- **6.3 Crash logs are invisible to you. Low to Medium.** They're written to `files/crash-logs/`, but there's no way to see them, which the spec puts in Settings. In an AI-built app, a crash log you can share is the fastest way to a fix.
- **6.4 Small gaps (Low):**
  - there's no setting for when your day starts (it's midnight until then);
  - the app has no icon;
  - after the system kills the app in the background, you land on Home rather than where you were.
