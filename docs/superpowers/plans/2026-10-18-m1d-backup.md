# M1d — Backup and Restore Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the three backup layers the design requires before the first usable release: Android Auto Backup, a daily database snapshot to a folder the user picks, and manual export and restore (JSON or database file) from Settings. Close M1 with the exit drill: enter weights, export, wipe the app, restore, and get identical data.

**Architecture:**
- **`:core:importers`** (pure Kotlin) owns the `ExportBundle` JSON format (schema v1): kotlinx.serialization records, encoding and decoding, and the row checks.
- **`:core:backup`** (Android) owns the file plumbing and has no Room types:
  - `VACUUM INTO` snapshots and the checks a snapshot file must pass;
  - staging a restore and installing it before Room opens;
  - the Storage Access Framework (SAF) folder;
  - the WorkManager worker and its scheduler.
- **`:core:data`** owns:
  - the mapping between Room entities and bundle records;
  - the JSON merge (by `id` and `updatedAt`);
  - `DefaultBackupRepository`, which implements the `:core:domain` `BackupRepository` that Settings uses.
- **`:app`** binds everything and restarts the process after a full restore.

**Tech Stack:**
- Kotlin 2.4.21; kotlinx.serialization 1.11.0 (JSON, plus its built-in `Uuid` and `Instant` serializers); kotlinx-datetime 0.8.0.
- Room 2.8.5 (SupportSQLite `execSQL`).
- New dependencies: WorkManager (`androidx.work:work-runtime`, `work-testing`) and `androidx.hilt:hilt-work` with `androidx.hilt:hilt-compiler`.
- Activity Result contracts: `CreateDocument`, `OpenDocument`, `OpenDocumentTree`.
- Testing: Robolectric 4.17, Turbine.

**Spec:** `docs/initial_design.md`:
- decision #21 (Export);
- "Backup, export and the sync seam" (Backup layers, JSON export format);
- "user.db schema" (standard columns, `originDeviceId`);
- "Module architecture" (`:core:backup`, `:core:importers`);
- "Testing strategy" (JSON export round trip);
- roadmap M1 and its exit criterion;
- "Risks" (data loss, migration bug).

This is plan 4 of 4 for M1 (M1a → M1b → M1c → **M1d**). `v0.1.0` is tagged after it merges.

## Calls made in this plan

1. **One Backup section in Settings,** below Units. It has four rows:
   - **Daily backup:** "Choose folder" / "Change folder", "Back up now", and a status line.
   - **Export data:** saves JSON.
   - **Export database copy:** saves a `.db` file.
   - **Restore from a file…**

   A result message ("Exported 42 entries", "Restored: 3 added, 1 updated") appears under the section heading as a polite live region, so no snackbar plumbing is needed.
2. **Restore accepts either kind of file and detects which it is.** A file starting with the 16-byte SQLite header `SQLite format 3\0` is a snapshot, which **replaces** all data. Anything else is read as JSON, which **merges**. Before restoring, a preview dialog shows how many entries the file holds and when it last changed.
3. **A full replace restarts the app.** The validated file is staged at `files/restore/staged.db`. Before staging, a safety copy of the current data is made with `VACUUM INTO` at `files/restore/before-restore.db` (one copy, overwritten each time). The process then restarts. On the next start, before Room opens, the staged file replaces `user.db`, and the old `-wal` and `-shm` files are deleted. This also handles the deferred item "invalidate `SingleLocalOwnerProvider`'s cached owner", because a new process has no cache.
4. **A JSON merge adopts the bundle's rows into the current owner.** A fresh install has already made its own empty profile, so every imported row's `ownerId` is rewritten to the local owner. The bundle's profile fields are merged into the local profile by `updatedAt`, and the local profile keeps its `id`. v1 has one user per phone, so this cannot mix two people's data.
5. **The merge rule** applies to each row:
   - When the `id` is unknown, the row is inserted.
   - When the bundle's `updatedAt` is later than the local row's, the bundle row replaces it, tombstones included.
   - Otherwise the local row is kept.
   - **Rows with a natural key merge by that key** when the `id` differs, and the newer one wins in place, keeping the local `id`:
     - a day-start setting matches by `effectiveFrom` (its unique index spans tombstones, which is the deferred item);
     - a measurement with a non-null `externalId` matches by `(source, externalId)`, so the same Health Connect record imported on two installs never trips the unique index (review §2.3).

   Imported rows keep their `createdAt`, `updatedAt`, `deletedAt` and `originDeviceId`, and get the stamp's `localRevision`. Re-importing the same file therefore changes nothing. The whole import is one transaction: the file is validated first, and if any row fails, nothing is written.
6. **The JSON covers `user.db` user data only:** profiles, day-start settings, user-defined measurement types (built-ins excluded) and measurements. It leaves out `SyncSequence`, `SyncCursor`, `DatasetVersion` and `localRevision`, which belong to the device. Preferences (unit, theme, ranges) are not in the JSON; Auto Backup carries them.
7. **Snapshot checks:**
   - the SQLite header;
   - `PRAGMA quick_check` = `ok`;
   - `PRAGMA user_version` is at most the current version: a higher value means "made by a newer GetFit", and a lower one is restored and then migrated by Room when it opens (review §2.2);
   - `room_master_table.identity_hash` equals the hash recorded for *that* version in `USER_DATABASE_IDENTITY_HASHES` (call 8);
   - every `DayBoundarySetting.dayStartMinutes` is in 0..1439;
   - every `Measurement.timeZone` is an ID kotlinx-datetime accepts;
   - every `MeasurementType.canonicalUnit` is a code `measurementUnitOf` accepts (Task 1).
8. **Pin the schema now:** `USER_DATABASE_VERSION = 1` and `USER_DATABASE_IDENTITY_HASHES: Map<Int, String> = mapOf(1 to "0cf6a91b7d0c77f034d4018880010478")` live in `:core:database`. Each later version adds an entry and never removes one, so snapshots from every past version stay restorable. `SchemaJsonTest` asserts that the entry for the current version matches both the committed `1.json` and the compiled database. From `v0.1.0` on, any schema change fails that test until the version is bumped with a numbered migration and a `MigrationTestHelper` test (deferred item; the first migration arrives with M2).
9. **Daily snapshots:**
   - **File name:** `getfit-snapshot-yyyyMMdd-HHmmZ.db`, in UTC: local time can repeat an hour when clocks fall back, and pruning goes by name (review §2.6). It has no colons, which some document providers reject.
   - **Retention:** the newest **14** are kept. Pruning touches only files matching that pattern.
   - **Schedule:** unique periodic work named `getfit-daily-snapshot`, repeating every 1 day, requiring charging and storage not low, with policy UPDATE.
   - **Lifecycle:** scheduled when a folder is chosen, and checked at every app start (KEEP). It is not cancelled when the folder becomes unusable: the worker records the failure and tries again the next day.
   - **Catch-up:** when the app starts and a folder is set but the last success is more than 36 hours old, a one-time snapshot is enqueued. Samsung's battery management can delay periodic work for apps it thinks are unused (review §2.5).
   - **Google Drive works as the folder:** confirmed by the owner on the S25 on 2026-10-18 (review §2.1).
10. **Status lives in DataStore** (`BackupSettingsDataSource`): the folder URI, its display name, the time of the last success, and the reason for the last failure. A failed run returns `Result.failure()` after recording why, so WorkManager never retries in a tight loop. A folder whose permission is gone (revoked, or restored onto a new phone by Auto Backup) shows "Can't reach the backup folder. Choose it again."
11. **Auto Backup:**
    - `res/xml/data_extraction_rules.xml` has identical `<cloud-backup>` and `<device-transfer>` sections. Each includes `database/user.db`, `database/user.db-wal` and `file/datastore/`. Explicit includes leave everything else out: crash logs, `reference.db` and the `restore/` folder.
    - The device ID is safe without an exclude, because it lives in `noBackupFilesDir`.
    - The system stops the app before a full backup, so the database and its WAL file are consistent.
12. **Corrupt `user.db` is preserved.** Room's default handling deletes a corrupt database, so a wrapping open-helper callback first copies the file to `files/corrupt/user-<epochMillis>.db` and then lets the default handling run.
13. **Startup hardening (deferred items):**
    - A failed `DataBootstrap.run()` is caught (not `CancellationException`), logged through the new `Logger` (call 20), and does not kill the process.
    - `FileDeviceIdProvider` treats an `IOException` on read as a missing file.
    - `LocalProfileDao` orders by `createdAt, id`.
14. **Out of scope:** a crash-log viewer, editing the snapshot count, encryption, and preferences in the JSON.
15. **Stored units come from a fixed list** (owner decision, 2026-10-18, made before the schema is pinned):
    - `MeasurementType.canonicalUnit` holds a code from one list. Each unit belongs to a dimension, and the dimension decides which display-unit setting applies: mass uses the existing weight unit; length gets a setting when circumferences arrive (M2).
    - The column stays `TEXT`, so the schema identity hash doesn't change.
    - User-defined lab markers keep any label as `custom:<label>`, with no dimension and no conversion.
    - **Stored meanings are fixed now, for every later type:**
      - lengths in meters;
      - body fat and every other percentage as a fraction from 0 to 1;
      - masses in kilograms.

    See "Schema notes for later milestones" in `docs/initial_design.md`.
    - **The list grows; codes are permanent.** Later milestones add units, such as milliliters, breaths per minute, °C, g, mg, µg and IU. A code, once shipped, never changes meaning or spelling (review §1.3).

The calls below were added on 2026-10-18 from the pre-v0.1.0 review (`docs/reviews/2026-10-18-pre-v0.1.0-review.md`):

16. **Typed units get codes too.** `Measurement.enteredUnit` stores a `DisplayUnit` code from one list in `:core:model`: `lb`, `kg`, `cm`, `in`, `%` to start, growing like `StandardUnit`. It was free text produced by `:feature:body`. Import and restore checks validate it (review §1.2).
17. **Stored enum names are pinned.** Room and the JSON export store `MeasurementSource`, `MeasurementCategory`, `DailyAggregation` and `Sex` by constant name. A test in `:core:model` pins each enum's names, so renaming a constant fails CI instead of making old rows unreadable (review §1.1).
18. **Built-ins are upserted when the dataset version rises** (review §1.4).
    - Built-in measurement types are owner-less reference data with `localRevision = 0`, so a correction (decimals, display name, Health Connect record type) can ship in a release.
    - Users can't edit built-ins, so nothing user-owned is overwritten.
19. **A stored time zone the device doesn't know never breaks a read** (review §5.3).
    - `Converters.timeZoneFromId` returns `TimeZone.UTC` for an ID it can't resolve, instead of throwing and failing the whole query.
    - The stored text itself is untouched unless that row is edited.
    - Restore checks still reject unknown zones (call 7, Task 2), so this only guards rows written on a device with newer time-zone data.
20. **Logging arrives with the first background work** (review §5.2). A `Logger` interface in `:core:model` (`debug`, `info`, `warn`, `error(message, throwable?)`) with a `FileLogger` in `:core:data`:
    - it writes to `files/logs/getfit-<yyyyMMdd>.log`;
    - it keeps 7 days and caps each file at 512 KiB;
    - it is bound in `:app`.

    The worker, the bootstrap guard, the restore installer and the backup repository log through it. A log viewer stays in the backlog with the crash-log viewer.
21. **The app version comes from the package,** not `BuildConfig`, which this project doesn't enable. `AppVersion` is read with `PackageManager.getPackageInfo(packageName, 0).versionName` in `:app` (review §2.4).
22. **The restart uses a separate restart process** (the ProcessPhoenix pattern) rather than `exit(0)` straight after `startActivity`, which can race (review §2.8).
    - It is a tiny `RestartActivity` declared in its own `:restart` process.
    - The main process starts it, then kills itself.
    - The activity relaunches the main task and finishes.
23. **0.1.0 is the release build.** Task 10 does three things before the tag (review §1.5, §1.6, §5.6):
    - bumps `VERSION_NAME` to `0.1.0`;
    - installs the release APK on the S25 and repeats the exit drill there;
    - does the TalkBack listening pass.

## Review Focus

1. **Restoring a JSON file on a fresh install that already made its own profile.** All weigh-ins appear under the current owner, no second profile is created, and Home and Body show them immediately. Pinned in Task 5: `merge_freshInstall_adoptsRowsIntoLocalOwner`.
2. **Importing the same JSON file twice.** There are no duplicates, and the second import reports every row unchanged. Pinned in Task 5: `merge_sameBundleTwice_secondChangesNothing`.
3. **A file that is neither kind:** a photo, truncated JSON, another app's SQLite database, or a backup from a newer GetFit. The user gets a clear message and nothing changes. Pinned in Task 4 (`inspect_otherAppsDatabase_isNotGetFit`, `inspect_newerVersion_isNewer`) and Task 6 (`inspect_photo_isUnreadable`, `restore_truncatedJson_changesNothing`).
4. **A backup folder that is unusable** (permission revoked, folder deleted, or a new phone after Auto Backup). The worker records "folder unavailable", the app doesn't crash, Settings asks the user to choose the folder again, and the next run retries. Pinned in Task 6 (`backUpNow_folderGone_recordsFolderUnavailable`) and Task 7 (`worker_jobFails_returnsFailureWithoutThrowing`).
5. **The process dies between staging a restore and restarting.** The next launch installs the complete staged file, never half a file, and a leftover temporary file is ignored. Pinned in Task 4: `install_onlyCompleteStagedFile_isInstalled`.
